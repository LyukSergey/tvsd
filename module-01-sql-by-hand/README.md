# Module 01 — SQL руками

Перш ніж доручати роботу з базою якомусь фреймворку, треба самому розуміти, **що таке
таблиця, зв'язок і запит**. У цьому модулі ми не пишемо жодного рядка Java — лише працюємо
з базою **PostgreSQL** напряму мовою **SQL**: створюємо таблиці, наповнюємо даними
й навчаємося писати запити, включно з агрегацією через `GROUP BY`.

Усе, що ви тут напишете руками, пізніше згенерує за вас Hibernate. І щоразу ви впізнаватимете
цей самий SQL у логах — тому фреймворк не буде «чорною скринькою».

## Що навчимося
- Створювати таблиці (`CREATE TABLE`) і розуміти **первинний** та **зовнішній** ключі.
- Бачити **зв'язки між таблицями**: 1:N та N:M на прикладі магазину.
- Наповнювати таблиці (`INSERT`).
- Писати запити: `SELECT`, `WHERE`, `ORDER BY`, `JOIN`.
- Розуміти, **як будується SQL-запит** — порядок і призначення його секцій.
- Рахувати підсумки: **`GROUP BY`**, `COUNT/SUM/AVG`, `HAVING`.

## 1. Запуск бази

У цій теці лежить `docker-compose.yml`. Піднімаємо базу:

```bash
docker compose up -d
```

Перевіряємо, що контейнер працює:

```bash
docker ps
```

Має бути рядок з образом `postgres:16` і статусом `Up`.

## 2. Підключення до бази

Є два способи. Достатньо будь-якого.

### Спосіб А — термінал (psql усередині контейнера)

```bash
docker compose exec db psql -U shop -d shop
```

- `docker compose exec db` — виконати команду всередині контейнера з ім'ям `db`.
- `psql -U shop -d shop` — запустити клієнт `psql`, користувач `shop`, база `shop`.

Ви потрапите в інтерактивний режим із запрошенням `shop=#`. Корисні команди psql
(вводяться без крапки з комою):
- `\dt` — список таблиць;
- `\d products` — структура таблиці `products`;
- `\q` — вийти.

### Спосіб Б — DBeaver (графічно)

Створіть нове підключення PostgreSQL із параметрами: host `localhost`, port `5432`,
database `shop`, user `shop`, password `shop`. Далі відкривайте SQL-редактор і виконуйте запити.

## 4. Таблиці та зв'язки магазину

Ось наша схема. Стрілка `──<` читається як «один до багатьох».

```
  categories                 products
  ┌────┬─────────┐           ┌────┬──────────────┬────────┬──────────┬─────────────┐
  │ id │ name    │           │ id │ name         │ price  │ quantity │ category_id │
  ├────┼─────────┤           ├────┼──────────────┼────────┼──────────┼─────────────┤
  │ 1  │ Phones  │ ──┐       │ 1  │ iPhone 15    │ 999.00 │    10    │      1 ─────┼──┐
  │ 2  │ Laptops │   │       │ 4  │ MacBook Air  │1199.00 │     5    │      2      │  │
  └────┴─────────┘   │       └────┴──────────────┴────────┴──────────┴─────────────┘  │
                     └──────────────────────── 1 категорія ──< N товарів ─────────────┘
```

**Два види ключів:**
- **Первинний ключ (PRIMARY KEY)** — стовпець `id`, унікальний номер рядка. За ним база
  знаходить конкретний запис.
- **Зовнішній ключ (FOREIGN KEY)** — стовпець, що **посилається** на `id` іншої таблиці.
  Наприклад, `products.category_id` вказує на `categories.id`. База не дасть вставити товар
  із неіснуючою категорією — так гарантується цілісність даних.

**Типи зв'язків у нашому магазині:**

| Зв'язок | Тип | Як зроблено |
|---|---|---|
| Category → Product | 1:N (один-до-багатьох) | `products.category_id` → `categories.id` |
| Customer → Order | 1:N | `orders.customer_id` → `customers.id` |
| Order → OrderItem | 1:N | `order_items.order_id` → `orders.id` |
| Product ↔ Order | **N:M** (багато-до-багатьох) | через проміжну таблицю `order_items` |

> **Чому N:M потребує окремої таблиці.** Одне замовлення містить багато товарів,
> і один товар трапляється в багатьох замовленнях. У реляційній базі такий зв'язок
> не можна виразити одним стовпцем — потрібна **зв'язкова таблиця** `order_items`,
> де кожен рядок поєднує одне замовлення з одним товаром (та ще й зберігає кількість і ціну).

## 5. Як будується SQL-запит

Це найважливіша частина модуля. Повна форма `SELECT` має фіксований **порядок секцій**:

```sql
SELECT   -- які стовпці вивести
FROM     -- з якої таблиці
JOIN     -- які таблиці приєднати і за якою умовою
WHERE    -- якими рядками обмежитись (фільтр ДО групування)
GROUP BY -- як згрупувати рядки
HAVING   -- фільтр ПІСЛЯ групування (працює з агрегатами)
ORDER BY -- як відсортувати результат
LIMIT    -- скільки рядків повернути
```

Але пишемо ми в одному порядку, а база **виконує** в іншому:

```
   FROM / JOIN  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  ORDER BY  →  LIMIT
```

Саме тому, наприклад, у `WHERE` не можна використати псевдонім стовпця, заданий у `SELECT` —
на момент `WHERE` база ще не дійшла до `SELECT`.

### Приклад «нарощування» запиту

```sql
-- крок 1: усі товари
SELECT * FROM products;

-- крок 2: лише потрібні стовпці
SELECT name, price FROM products;

-- крок 3: + фільтр
SELECT name, price FROM products WHERE price > 500;

-- крок 4: + сортування і обмеження
SELECT name, price FROM products
WHERE price > 500
ORDER BY price DESC
LIMIT 3;
```

### JOIN — поєднання за зв'язком

```sql
SELECT p.name AS product, c.name AS category
FROM products p
JOIN categories c ON c.id = p.category_id;   -- умова з'єднання = рівність FK та PK
```

- `p`, `c` — псевдоніми таблиць (щоб писати коротше).
- `INNER JOIN` (просто `JOIN`) лишає тільки рядки, для яких є пара в обох таблицях.
- `LEFT JOIN` лишає **всі** рядки лівої таблиці; якщо пари немає — праві стовпці `NULL`.
  Саме так ми побачимо клієнтку Carol, у якої немає замовлень.

Усі ці запити з поясненнями — у `sql/03-select-basics.sql`.

## 6. Агрегація: GROUP BY

Коли треба не окремі рядки, а **підсумок** (скільки, на яку суму, середнє) —
використовують агрегатні функції й `GROUP BY`.

```sql
-- скільки товарів у кожній категорії
SELECT c.name AS category, count(p.id) AS products_count
FROM categories c
JOIN products p ON p.category_id = c.id
GROUP BY c.name
ORDER BY products_count DESC;
```

```
 category    | products_count
-------------+----------------
 Phones      |       3
 Accessories |       3
 Laptops     |       2
```

**Правило GROUP BY:** усе, що у `SELECT` стоїть **поза** агрегатною функцією,
має бути перелічене в `GROUP BY`.

**`HAVING` проти `WHERE`:**
- `WHERE` фільтрує **окремі рядки ДО** групування.
- `HAVING` фільтрує **готові групи ПІСЛЯ** групування (може використовувати агрегати).

```sql
-- тільки категорії, де більш ніж 2 товари
SELECT c.name, count(p.id) AS cnt
FROM categories c
JOIN products p ON p.category_id = c.id
GROUP BY c.name
HAVING count(p.id) > 2;
```

Приклад суми кожного замовлення (`SUM(quantity * unit_price)`), середніх цін та `HAVING` —
у `sql/04-group-by.sql`.

## Типові помилки

| Повідомлення / симптом | Причина | Як виправити |
|---|---|---|
| `relation "products" does not exist` | Таблиці ще не створені | Спершу виконайте `01-create-tables.sql` |
| `insert or update ... violates foreign key constraint` | Вставляєте рядок із `category_id`/`customer_id`, якого немає | Спочатку вставте батьківський рядок (категорію/клієнта) |
| `column "p.name" must appear in the GROUP BY clause ...` | Стовпець у `SELECT` поза агрегатом, але не в `GROUP BY` | Додайте його в `GROUP BY` або оберніть агрегатом |
| `syntax error at or near ...` | Пропущена кома/дужка, зайва крапка з комою | Перечитайте запит; виконуйте по одному |
| `password authentication failed` | Невірні логін/пароль | Перевірте, що user/password = `shop`/`shop` |

## Завдання для самостійного виконання

Напишіть **руками** п'ять запитів до бази магазину:

1. Усі товари дорожчі за 100, відсортовані за ціною спадання.
2. Назва товару + назва його категорії (`JOIN`), лише категорія `Phones`.
3. Усі клієнти та кількість їхніх замовлень (`LEFT JOIN` + `GROUP BY`), включно з тими, у кого 0.
4. Сума кожного замовлення (`SUM(quantity * unit_price)` + `GROUP BY`), найдорожче — зверху.
5. Категорії, у яких середня ціна товару перевищує 500 (`GROUP BY` + `HAVING`).

Перевіряйте результат очима: чи логічні числа, чи немає «зайвих» або «загублених» рядків.
